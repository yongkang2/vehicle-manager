# 发布一致性方案（草案）

日期：2026-11-04。目标：用户看到的正式版本明确唯一，源码、包和线上发布可以核对，发布流程主动拒绝不一致。

## 已查明的现状

- GitHub 最新正式版为 v1.2.1，本地当前分支源码为 1.1.4。本地信息不足以判断线上最新版。
- 历史 1.0.2 Release 的标题为 1.0.2，标签和附件名却含 1.0.1。
- 本地有一个未正式发布的 1.1.3 和两个不同构建时间的 1.1.4；线上 v1.1.4 只保留了最终构建 20261103095332。
- 正式发布中没有 1.1.3、1.1.5、1.2.0。1.2.1 发布说明解释：部分团队门槛已达开发版本 1.2.0，因此修复版本必须高于它。
- 当前本地打包脚本支持单独覆盖包版本，仅重写服务端生成版本；已构建的前端可能仍显示原版本。这是应移除的多版本来源。

## 路线选择

1. 只写人工清单：改动最少，但容易再次漏检。
2. 保留现有工具，增加统一版本与发布校验：推荐，复用已有打包、验收及 GitHub CLI。
3. 全面重做 CI/CD：可进一步自动化，但当前没有必要增加维护范围。

## 推荐流程

1. 从最新远程正式发布及其集成后的源码开始，确认分支包含上一正式版本，避免仅依据版本数字发布遗漏旧修复。读取团队版本门槛的已知证据；不要为了版本整齐降低团队门槛。
2. 只修改 package.json 的版本，通过现有机制同步锁文件与 shared/version.ts。生成标签、标题、ZIP 名及发布说明时读取同一版本；取消打包专用版本覆盖。运行时版本覆盖也不能改变正式交付身份。
3. 保持现有测试、lint、build 和解压包业务验收。新增一致性检查，核对源码版本、生成版本、包内版本、服务端实际响应及前端使用的生成版本。优先在构建时生成轻量版本信息供校验，避免从压缩 JS 中猜测版本。
4. 本地成功构建后，生成发布记录：应用版本、精确源码提交、ZIP 文件名、SHA-256、验证结果。时间戳仅表示构建时间，不代表另一个应用版本。允许未发布时重试构建，但只选一个通过验收的最终包交付。
5. 发布入口再次核对远程状态：版本未发布、标签未被占用、源码可追溯且包含上一正式版、产物校验通过。生成草稿 Release，附最终 ZIP、校验和与发布记录；所有身份信息来自同一版本。重试时核对已有草稿和校验和，不能覆盖不同内容。
6. 正式发布前完成审阅；发布后读取线上元数据并下载附件核对 SHA-256。失败则明确报告状态，不宣称成功，不通过替换已发布包掩盖问题。只有验证通过的最新正式版设为 Latest。

## 历史整理

- 保持 v1.2.1 作为当前正式入口，在说明中补充正式版本沿革及跳号原因。
- 给标题写 1.0.2、实际附件写 1.0.1 的历史 Release 加上“历史版本标识不一致，已弃用”说明，保留原资产与标签。
- 本地两份 1.1.4 和未发布的 1.1.3 按“临时构建”与“正式产物”区分；未经单独授权不删除文件。以后临时目录与交付目录分开。
- 应用下载入口继续链接 GitHub Releases，无需新增自动更新系统。

## 验收标准

- 任意一个应用版本来源、标签、包名不一致时，打包或发布失败。
- 对已正式发布版本再次交付不同内容时失败；远程查询失败时停止发布。
- 从不包含上一正式版本的分支发布时失败；预发布不能设为 Latest。
- 一个最终包能追溯到精确源码提交；线上下载的 ZIP 校验和与本地验收产物一致。
- 常规用户只需识别应用版本；数据库结构、共享协议等内部版本在必要的兼容性说明中单独解释。
