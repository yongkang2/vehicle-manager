# Development and implementation notes

This source targets **application 1.8.0**; verify published builds on GitHub Releases. Its current compatibility contract is local schema **6**, shared business protocols **1–5**, and newly written business backup **format 5 / field version 4**, with readers for backup formats **1–4**. Published packages and release acceptance must be verified separately; this document does not claim real Windows SMB multi-computer validation for the new workflow.

Integrated business build. React + TypeScript + Ant Design, Node.js 24 + Express, local SQLite. Download the [latest official release](https://github.com/yongkang2/vehicle-manager/releases/latest); see [version history and release rules](releases.md). The source version is defined in package.json.

## Current Scope

This independent application now includes the agreed vehicle business workflows. Real company Windows/SMB acceptance is still required before production deployment. The existing `vehicle-demo` and `dove-import-preview` are not modified.

Implemented: local registration/login, English default with Chinese selection, persisted language choice, deferred shared-folder setup, read/write/rename checks, explicit team creation, join requests, administrator approval/rejection, existing-identity device binding, role changes, account disablement, device revocation and last-effective-administrator protection. Team management always reads the live shared roster under an exclusive lock; credentials and login sessions remain local. Team rollback detection is also applied before management writes.

Also implemented: vehicle CRUD; structured controller/motor/battery parts; Vehicle Modification with independent copies, linked groups and retained files; separate equipment records; installation/removal dates; authenticated attachments; field-level change history; admin-only archiving and restoration; shared business snapshots and conflict handling; DOVE preview/VIN matching/original retention; same-VIN controller and fault comparison; explicitly selected configuration updates with report provenance; JSON export; admin backup and forward restore; local security audit; portable Windows x64 packaging. No vehicles, reports or accounts are seeded.

Not claimed: arbitrary DOVE template compatibility, fault occurrence statistics, automatic diagnosis/release decisions, tamper-proof authorization, automatic disaster recovery, password recovery, scheduled independent backups, instant offline revocation or company endpoint/SMB approval. Original-file storage is private but not encrypted by this application; use approved disk/share protection.

## Build and Run

```powershell
npm ci
npm run build
npm start
```

Open http://127.0.0.1:4410 . The application listens on the local loopback address only. Change `PORT` if this port is occupied. Local data defaults to `%LOCALAPPDATA%\VehicleManager\data`, independently of the extracted application folder; `VEHICLE_MANAGER_DATA_DIR` can select another dedicated local directory. On first start, the launcher safely migrates data from this folder or one adjacent older `vehicle-manager-*` release, verifies the copy, then renames the source to a `data.migrated-backup-*` folder. Stop the old version with its matching `Stop.cmd` first. If several old data folders are found, the newest-used one is migrated and the others are logged as ignored (also recorded in `data/.data-migrated`); use `VEHICLE_MANAGER_DATA_DIR` when a different one is authoritative. The old Demo's 4310 port is not used.

Double-click `Start.cmd` to start in the background and open the browser. It reuses the service for this data directory, or chooses a free local port. The service checks open application pages every five minutes and stops gracefully once none remain, with a short reconnect grace period for refresh/navigation. Closing one tab does not stop a service still used by another app tab; hidden, minimized or inactive pages remain connected. A server with no app page opened also stops after the initial five-minute check. Reopen the application with `Start.cmd` after an automatic stop. `Stop.cmd` still verifies the same instance and requests an immediate clean stop; it does not kill unrelated Node.js processes. Pending synchronization settles before the local database closes; offline changes remain queued on disk. The launcher and `npm start` should not be used concurrently for the same data directory. Local `service.json` contains a stop-control secret; do not share it or `data/`.

On Windows, a per-data-directory named pipe serializes launchers and releases automatically if a launcher crashes. Concurrent starts wait for up to 60 seconds; old empty startup locks recover after a five-second grace period, while live owners and nonempty unreadable locks remain protected. A failed existing-service probe gets one additional five-second verification attempt. Only an explicit `EADDRINUSE` startup error retries a new port; other failures stop immediately with the exit code or error and full log paths. Failures before service initialization are recorded in `launcher.log` when writable, including missing package metadata. The launcher reports log-write failures in the console.

For development, run `npm run dev:server` and `npm run dev` in separate terminals. Vite uses 4411 and proxies API requests to 4410. Starting another application version against an already-running data directory is refused; stop the existing service with its matching `Stop.cmd` before upgrading.

## First Launch and Shared Path

1. Create a local account; passwords must be 10–128 characters. There are no default credentials. The login and registration screen credits **Developer: TA98755**; this is recognition only, not an account or permission.
2. If the company share is not ready, choose **Set up later**. The path remains unconfigured; no simulated share is silently connected and no remote root is created.
3. Once the share exists, enter a UNC path such as `\\fileserver\team\vehicle-data` and test the connection. The signed-in Windows account must already have SMB/NTFS access. The application does not ask for or store Windows credentials.
4. An existing, empty, dedicated folder may explicitly initialize a team after confirmation. The current account becomes the first administrator. A directory containing another application's files, including the previous Demo's snapshots, is not overwritten or adopted automatically.
5. For an existing team, submit a join request. An approved administrator must verify the person/device and choose a new member identity or bind it to an existing identity. The first local account on another computer is not automatically an administrator.
6. Use the bottom-left account button to open **Personal workspace**. Each login session selects its own team; accounts and passwords remain local. Connect additional teams or switch between connected teams without clearing existing data. A team is identified by its roster ID, not its name or folder path.

The share contains a versioned `team.json` roster and a transient `.vehicle-manager-team-lock/` directory during writes. Approved clients additionally maintain `business/HEAD.json`, immutable `business/snapshots/`, unique `business/operations/` and content-addressed `business/blobs/`. Team and business writes use the same exclusive lock. SQLite merge work is performed on a local temporary copy, not by multiple clients writing a network SQLite WAL. Do not edit shared protocol files manually. Real SMB behavior still needs multi-computer validation.

The team lock is an operation-scoped lease, not a login/session lock. Contenders retry with jitter for up to three seconds before reporting busy. Each owner has a uniquely named lease file recording its token, computer, process and creation time, renewed every ten seconds. After two minutes without renewal, another operation can reclaim abandoned lease files, legacy `owner.json` locks and incomplete empty locks. Recovery compares file timestamps with a temporary file on the same share rather than the client's wall clock. Release removes only the owner's unique file and attempts a non-recursive removal of the empty lock directory; it never recursively deletes a successor's lock or unknown contents. Preserved `.saved-*` lock folders are not active locks and are not automatically deleted.

Team roster and business atomic publication revalidate ownership immediately before renaming their prepared files into place. A lost, unreachable or locally expired lease stops further publication with `SHARE_LOCK_LOST`; suspension longer than the renewal deadline cannot silently resume writing. Completed publications are not rolled back: reconnect, synchronize and check the result before retrying. Background sync retries on its normal schedule, and permanent-deletion retries retain their idempotency request ID. Recovery does not discard local pending edits or modify roster/business formats.

Deploy this locking update to **all collaborating clients together**: stop every old service and independently back up the shared folder and local data first. Older clients do not renew leases, so their long operations cannot safely coexist with automatic stale-lock recovery. After upgrade, abandoned known-format locks recover on the next operation after the two-minute grace period; no manual deletion is needed. Unknown contents or insufficient delete permissions require administrator investigation, not force deletion. This remains a filesystem lease, not a server-enforced fencing transaction: it assumes one coherent SMB namespace with atomic directory creation/rename and timely metadata visibility. Do not use independently synchronized OneDrive/offline replicas or split-brain storage as the team share. Strict exclusion through arbitrary network partitions or pauses between the final check and rename requires a central transactional service; it is not guaranteed by this deployment model.

Before a breaking team-format upgrade, first install the new release on every device and create a cold backup. An administrator can then enable **Require current version** from **Team access > More**; this switches the shared roster to protocol 2 and older releases will be rejected. The action requires two effective administrators so the team retains an approval path. Shared snapshots retain the latest 30 and one per day for 90 days; attachments and original blobs are not currently garbage-collected. Backup restore requires a preview, explicit confirmation of omitted records to archive, and acknowledgement of fields this version does not understand. The preview is invalidated if the backup, local records, deletion markers or pending operations change before restore.

Pending or disabled accounts cannot access the administrator API. Offline status may display the last approved cached identity, but all administrator operations require a successful live shared-folder read. People who can modify the share or local SQLite can bypass normal application controls; this is not tamper-proof enterprise authentication. Copy application code to another computer, not `data/`, session files or another device's identity.

## Personal Workspaces (First Version)

**Personal workspace** contains the team list, connect-another-team, withdraw-request, disconnect-session, resume-sync and sign-out actions. On mobile, use the person icon in the top bar. Business navigation and administrator team management remain separate. Account profile/password editing and permanent workspace deletion are not part of this version.

Team databases, originals, sync cursors, pending operations, conflicts and temporary DOVE previews are isolated. The original team keeps its local database and blob location; subsequent teams use `workspaces/<hashed-team-id>/` under the stable data directory. Moving the data directory to another computer also moves device identity and is not supported. Never copy an existing device identity to another computer. Each account sees only its connected teams; entering business data still requires approved team access.

Switching or disconnecting preserves all local data and does not revoke membership. Explicitly confirm retention if pending changes or conflicts exist. In-flight requests in the same session block switching, and stale pages cannot write after a switch or new login. Reload a stale page before continuing. Distinct sessions can select different teams; ordinary tabs sharing one login cookie also share its selection. The top bar identifies the current team. Selecting or logging back into a workspace with retained pending changes pauses synchronization until you review them and explicitly resume from the personal panel. Other active, sync-enabled sessions for that same workspace may still synchronize its queue. Existing live shared reads are required for administration; offline cached access retains the existing limitations.

Withdrawal updates only the current account/device's pending request under the roster lock; a withdrawn request cannot be approved. If approval wins the lock first, withdrawal fails rather than revoking the approved membership. If the original directory is unavailable, withdrawal fails honestly: you may disconnect locally and connect elsewhere, but ask the original administrator to reject or revoke the remote request. No background cancellation is silently scheduled.

Before first use with existing data, stop the old service and independently copy the complete data directory to a protected backup. Local SQLite schema is version **6**. Migration inspects the actual tables and columns: it supports both incompatible earlier schema-3 layouts (personal-workspace catalog/session structures, or permanent-deletion/quarantine structures), as well as schemas 4/5 and older supported databases, and adds the missing structures without dropping existing data. Workspace selections, identities, sessions, records, queues, conflicts, deletion receipts and quarantined operations are preserved. Before changing an existing database, migration creates and integrity-checks `migration-backups/before-schema6-<uuid>.sqlite` inside that database's local directory, then applies the upgrade transactionally. Nested workspace databases receive the same backup and shape-aware upgrade when first opened; fresh empty databases need no migration backup. Backup failure prevents migration, and interrupted transactions can retry. Database backups contain credentials and sessions and exclude separate blob files, so protect the complete data directory. They are not shareable business exports or independent disaster backups. Older application versions intentionally reject schema 6 and format-5 business backups. A new-format export cannot provide rollback compatibility with an older binary; rollback requires a stopped service and supervised restoration of a complete pre-upgrade backup, preserving all newer workspaces first. Do not replace a live SQLite file or delete WAL files.

API clients must retain the `X-Workspace-Token` returned on login/status and explicit selection changes and send it for setup configuration, business and team operations. Missing/stale tokens are rejected. Tokens are scoped to a login session and selection epoch; clients must not silently adopt a new token from background status calls over existing forms.

## Business Use

### Vehicle Modification

The former modification section is now **Vehicle Modification**. `modificationFields` adds optional **Requestor** (`requestor`) and **Lead** (`lead`) alongside name, description, **Start Date** and **Finish Date**; the date labels retain the existing stored fields. These fields do not belong to equipment. `VehicleModificationSection` owns the dedicated editor, expanded files, linked scope review and population dialogs; generic equipment editing remains separate. Before activation, Requestor and Lead inputs are disabled; basic names, descriptions and dates remain editable on records without enhanced values.

Stop all old services and independently back up the complete shared folder and every local data directory, including original blobs, before upgrading. After **all collaborating clients upgrade**, an online administrator with synchronization explicitly resumed chooses **Enable enhanced modifications** once for the workspace, with a reason. This publishes shared business protocol **5** and unlocks **Requestor, Lead, files and Linked mode together**. Existing Requestor/Lead values and pending work remain retained before activation, while writes/copies carrying nonblank values, restores of those values and their queued publication are blocked with `MODIFICATION_NOT_ENABLED`. Basic legacy records with blank Requestor/Lead remain editable and copyable; clients must not strip retained values to bypass the gate. Files and Linked mode also require activation. Protocol capability and configuration feature activation remain distinct: enabling enhanced modifications does not implicitly activate configuration revisions or component review policies. Unknown higher protocols require an upgraded client; no operation downgrades the shared protocol.

Files are attached only after the modification is saved. The queue accepts at most **8 files per batch**, **10 MB per file**, and exactly `.doc`, `.docx`, `.txt`, `.xls`, `.xlsx`, `.pdf`, `.eml`, `.msg`, `.7z`, `.zip`. `modification-files.ts` validates bounded format structure without executing files or extracting archives. Downloads retain original names and bytes. The existing sequential upload queue provides per-file outcomes and cancellation; an uncertain upload result requires refreshing and checking the saved file list before selecting it again. Only administrators archive or restore files.

**Populate to vehicles** searches eligible existing vehicles by partial VIN. No destination is selected automatically; a request explicitly identifies **1–100 destination vehicles**, their reviewed VINs, the source version and group version, the mode, one reason and one final confirmation. **One-time copy** creates independent rows with current fields, dates and active files. **Linked** creates or extends one canonical group: every linked vehicle shares all fields, dates and files, including Requestor and Lead. The review lists affected vehicles. Linked changes require connectivity, explicitly resumed synchronization and settled pending changes/conflicts; independent edits and one-time copies that meet these activation rules retain the normal offline outbox behavior.

Linked edits, files, population, unlinking and lifecycle changes use the shared maintenance gate, current authorization, version checks and atomic publication under the team lock. Per-request receipts bind the actor and command digest, allowing the same command to recover a lost response without duplicate application. **Unlink and keep independent copy** freezes this vehicle's current fields, dates and files; other memberships remain shared. Archiving a linked modification or its vehicle freezes only that vehicle's independent archived copy. Restoring it does not rejoin the group. Permanent deletion removes only the deleted vehicle's membership and preserves groups/files still used by other vehicles. History, JSON/CSV projections and backup files resolve linked values through the shared domain helpers.

Owners: `shared/modifications.ts`, `server/modifications.ts`, `server/modification-files.ts`, `server/modification-recovery.ts`, `server/modification-routes.ts` and `src/VehicleModificationSection.tsx`. Routes under `/api/business/modifications` expose status, administrator activation, detail/edit, file upload/download/archive, population, unlink and member archive. Modification fields and file metadata participate in history, sync and backup. CSV modification rows expose Requestor, Lead and group ID; attachment metadata rows expose modification/group/file IDs without embedding original bytes.

### Configuration revisions

Introduced in application 1.3.0, **Configuration revisions** are enabled once by an administrator for the selected workspace after collaborating installations upgrade. Activation requires at least shared business protocol 3 and preserves an already higher protocol; older clients cannot publish to an unsupported format. Existing team-roster upgrade rules remain in effect. Each vehicle starts without a published configuration and receives **R01, R02, R03…** only when an approved member publishes a review online with synchronization enabled.

Maintain HV Battery, eMotor, Controllers and Thermal Management in their component sections. Thermal System Type continues to use the existing vehicle value. Administrators can add named component types with common identification fields and notes and rename custom types. All active installed instances in included categories are captured, including multiple batteries/motors and legacy extra controller records.

In **Component types**, administrators can disable, remove and restore any category, including the four built-ins. Introduced in application **1.3.0**, the first policy change requires upgraded collaborating clients and atomically raises shared business protocol to at least **4**, preserving protocol 5 if already active. Disabled categories remain listed; removed categories appear under **Show removed**. Enable or Restore includes the same identity again. A reason and one final action confirm each change; built-in names and fields stay fixed. These policies affect future configuration reviews only: vehicle tabs, installed records and editing remain available, and nothing is physically deleted. Before policy activation, the older disabled-custom-type restriction on adding entries still applies.

Changing a relevant category's inclusion flags **Unpublished configuration changes**. Later edits to excluded categories do not. Reviews show excluded categories explicitly, and publication requires at least one included section. Published snapshots retain their frozen review scope, so history, comparisons and copied summaries distinguish exclusion from physical component removal. Old published snapshots remain unchanged. Historical policy-enabled format-4 backups use field version 3; current development backups use format 5 with field version 4. Older supported backups remain accepted and cannot overwrite current catalog decisions. Current local database schema is 6.

The review pre-fills existing values. Required missing information needs **Unknown** or **Not applicable** with an explanation; absent sections need **Not installed** or **Unknown** with a reason. These explanations belong to the frozen revision and do not rewrite ordinary component fields or DOVE observations. Enter a change summary and optional title, then use one final **Publish revision** action. Cancelling creates no revision; component edits already saved remain saved. Offline component work remains available, but publication requires an online, sync-enabled session; paused sessions must be resumed explicitly in Personal workspace.

Published revisions are read-only and retain VIN, actor, date, component identities and details. Compare revisions or copy their summary from the history tab. The Overview summary and optional **Configuration revision** table/CSV column show the current R number. Relevant component changes show **Unpublished configuration changes**; owner/location/photo changes, save counters and an identical DOVE reimport do not. Corrections create another revision, rather than editing an older one.

Current backup format 5 preserves frozen revisions, custom types, modification groups/files and durable publication receipts. Formats 1–4 remain accepted, including the historical format-4 configuration representation. Restoring old working data never archives or replaces published revisions, rolls their maximum R number back, or renames/reactivates current type definitions. Valid missing protected history is staged durably for publication with the working restore under the shared lock; conflicting immutable payloads, duplicate ordinals or broken chains reject restoration. Deleted vehicle UUIDs and their historical child rows remain skipped. Re-registering a VIN uses a new vehicle identity and a separate revision sequence.

Every labeled vehicle **Overview** field can be displayed through **Columns**, including **Compliance Level**. Optional **Nick Name**, **VIN** and **Plate valid until** columns show those values independently of the existing combined Vehicle and License plate columns. **Cooling architecture** can display stored legacy values without restoring that field to the editor. These five choices start hidden and support the same personal ordering, widths and header filters; the original ten default columns remain unchanged. Vehicle Photo and its attachment reference are excluded from the column catalog.

Use the filter button in any vehicle data-column header to search and tick distinct cell values, including **(blank)**, then choose **Apply**. **Reset** clears the checklist; apply it to remove that column's filter. Closing without applying keeps the current filter. Choices cover all vehicles permitted by **Show archived**, across every page. Multiple choices in a column use OR; different columns and the existing search/status/archive controls use AND. Combined cells are one choice, including nickname/VIN, plate/expiry, timestamp/version and joined battery summaries. Filtered headers are highlighted; **Clear column filters** removes all header filters. Hiding a column clears its filter, while resizing and reordering preserve it. Filters remain while navigating within the current account/workspace, but clear on reload, logout or workspace switching. They work offline and while sync is paused, use no saved settings or business writes, and do not change export configuration.

It is hidden by default, starts at 160 pixels wide and uses the existing personal visibility/order/width settings. It shows the same unarchived controller as the VCU slot, including the EVCU alias; a missing controller or blank legacy Type displays `—`. Editing the VCU Type updates the column when the records reload. This is a derived display, with no additional vehicle field or data migration.

The Vehicles table centers its headers and values. Open **Columns** to show/hide and reorder existing fields; Vehicle remains first and Actions last. Model, Color, Thermal System Type, Notes, HV Battery Part Number and HV Battery Serial Number are available in addition to the default columns. Drag a header's right edge to resize; double-click to restore its default width. Keyboard users can focus an edge and use Left/Right (Shift for larger steps), or Home/End for the minimum/maximum width. The layout saves automatically for the authenticated local account in the current workspace, including widths of hidden columns. Check the Saving/Saved status or Retry after a failure. Reset layout restores the default ten columns and widths. These personal settings survive restart but are not synchronized, included in business backups, or linked to CSV export templates.

Open a vehicle using the Action arrow to view its cover photo in Overview. Approved members can upload, replace or remove the cover with a change reason and version check; archived vehicles are read-only. Photos use JPEG/PNG, up to 10 MB, 8,192 pixels per side and 24 megapixels. The original bytes and metadata are retained, without cropping or metadata stripping. Replacing or removing a cover does not delete the old attachment, original blob, history or backup. Photos synchronize through the existing attachment workflow, and offline/paused changes remain queued without resuming synchronization. An unavailable selected photo is never substituted with another attachment. Business backups preserve the cover reference and attachment; older backups restore without a cover. When synchronization is enabled for the session, reads try synchronization first, successful local writes trigger synchronization, and the running service retries every 30 seconds. Offline saves remain queued. A paused session must review retained changes and explicitly resume in **Personal workspace**; permanent-deletion previews, permanent deletion and backup restore remain disabled until then. Backup downloads and read-only quarantine inspection/export stay available with their existing permissions. Other sync-enabled sessions for the same workspace may still synchronize its queue. Shared publication is eventual consistency, not a guarantee that every client updates within 30 seconds.
- Conflicting fields require local/shared choices. Duplicate VIN or an unavailable parent cannot be forced over a canonical shared record. Administrators can review blocked authorization conflicts, and the latest roster governs subsequent submissions. Do not copy a full local database over the shared snapshot.
- **Change history** contains synchronized business changes with actor/device/reason/source. **Device audit log** is administrator-only and displays this computer's login/download/export/backup events; it is not an immutable central security log.

## Administrator Vehicle Deletion and Upgrade

Archive remains reversible. An online administrator with synchronization enabled for the selected workspace can additionally delete an already archived vehicle from its detail drawer. If synchronization is paused, review retained changes in **Personal workspace** and explicitly resume before opening a deletion preview or confirming deletion. The five-minute preview lists the vehicle and all linked record counts; confirm the exact VIN, type `DELETE`, and enter a reason. Cancelling writes nothing. Pending target changes/conflicts must be resolved first, and changed vehicle/child data requires a fresh preview. Deletion removes the vehicle, controllers/parts, modifications, equipment, reports and attachments from current working data, including archived children. It does not purge original blobs, immutable snapshots, audit history or existing backups, and it is not secure erasure.

Deletion is published under the shared lock before success is reported. A dropped response can be retried with the same request; a committed deletion awaiting local refresh is not an ordinary failed deletion. Permanent deletion markers prevent stale offline edits, new offline children and old backups from resurrecting the old record IDs. Blocked local operations and their files remain quarantined: inspect/export them in **Shared sync**; there is no keep-local resurrection option. A VIN can be registered again with a new vehicle identity, and a fresh DOVE preview can retain the same original for that new identity without reviving deleted records.

Before deletion, configuration activation or activation of enhanced modifications, stop other installations, independently back up the shared folder and each local data folder, and upgrade all collaborating clients. The source application version is defined in package.json; this source targets application 1.8.0; published status is recorded on GitHub Releases. Local databases upgrade to schema **6** with integrity-checked migration backups. Business protocols **1–5** remain supported; deletion can upgrade protocol 1 to 2, configuration activation upgrades to 3, the first component review-policy change upgrades to 4, and the administrator action **Enable enhanced modifications** upgrades to 5. Synchronization, deletion and restoration never downgrade a protocol. Unknown higher protocols require a client upgrade. Team-roster protocols and policies remain independent. Never downgrade HEAD or delete shared files to resolve incompatibility.

The admin APIs are `GET /api/business/vehicles/:id/delete-preview` and `DELETE /api/business/vehicles/:id`; deletion uses an actor-bound preview, current version, exact VIN/confirmation/reason, and an idempotency request ID. Quarantined payloads are read-only at `/api/business/sync/quarantined` and can be exported at `/api/business/sync/quarantined/export`.

## Backup and Restore

Administrators can download an unencrypted ZIP containing records, synchronized history, pending operation payloads, referenced original blobs and a team-roster snapshot. It excludes local passwords and login sessions. Current safety limits are 200 MB total ZIP/expanded content, a 20 MB manifest and 10 MB per blob. Monitor disk capacity; old shared snapshots are retained and not automatically purged. A share snapshot is not a backup in a separate failure domain.

Restore is an online administrator operation: pause other clients and writes, independently preserve the current entire shared directory and local data, finish existing pending operations, select a backup from the same team, type `RESTORE`, and enter a reason. The current administrator session must have synchronization enabled; if paused, review retained changes and explicitly resume from **Personal workspace** before restoring. The application records forward business changes rather than rolling the shared sequence backwards; records outside the backup are archived, not physically deleted. New business changes after the backup may be replaced, so do not restore while others continue editing. Archived vehicles and retained originals are supported. Validate the restored records, history and files and then resume clients.

Current development backups always use **format 5, schema version 6 and field version 4**, including modification groups, memberships, files, durable command receipts and retained modification restore payloads. Formats **1–4** remain readable, including older schema-4/field-2 configuration backups and format-4/field-3 component policies. Current catalog decisions and published revision chains remain authoritative. Canonical deletion markers always win: restore skips deleted vehicle UUIDs and their linked records, reports skipped counts, and never clears markers or uses historical metadata to delete live records. Existing archive-extra-record behavior applies only to working records. Deleted-only original blobs remain retained but are not restored into working data.

Managed modification restoration stages the complete reviewed graph and receipts in `pendingModificationImports`, with reviewed base states and versions. Shared publication uses compare-and-swap: canonical record state must still match the reviewed base state, and a shared group's version must also match, before the graph is published under the team lock. A newer shared edit produces `MODIFICATION_RESTORE_CONFLICT`; it cannot be overwritten by retrying publication. Formats 1–4 preserve current managed modification identities rather than replacing them with legacy text rows; incompatible archive/detach effects are rejected.

On a guarded publication conflict, **Restore history** exposes **Export retained payload** and **Retain and review again**. The export contains the attempted/base payload and referenced files for investigation. With a reason and online administrator access, synchronization explicitly resumed, retention stores `abandonedModificationImports` before refreshing canonical shared data, removes the failed pending overlay and marks the receipt `MODIFICATION_RESTORE_REVIEW_REQUIRED`. Review a fresh backup preview before another restore. Retained payloads remain in business backups and can be exported through the recovery API; they are not silently replayed and never require rewriting shared HEAD.

The roster in the ZIP is preserved for manual identity/disaster investigation; the ordinary business restore UI does not roll back roles, reinstate revoked devices, replace local accounts or silently replay arbitrary historical pending-operation payloads. It restores the backup's record state through newly authorized operations. Lost roster/administrator credentials or incompatible/rolled-back protocol state require a coordinated manual recovery using independently preserved complete data, not pointing `HEAD.json` to an old snapshot and forcing clients onward.

## Configurable CSV exports

Use **Vehicles → Export CSV** to filter the local vehicle list, select vehicles across pages, and choose/reorder columns for vehicles, controllers, Vehicle Modification, equipment, report summaries and attachment metadata. Modification exports resolve shared fields and expose Requestor, Lead and group ID; attachment metadata includes modification files and their modification/group/file IDs. Different filters combine with AND; multiple values within one filter combine with OR. Archived vehicles and linked records are excluded unless **Include archived** is enabled. Choose English or Chinese headers. The download is always one ZIP with a CSV for each enabled category, including headers-only files when no linked rows exist. Original files, detailed DOVE controller/fault observations, historical snapshots, history and quarantined operations are not included; this export is not a backup.

Named templates remember filters, enabled categories, ordered columns, archive inclusion and header language. Applying a template selects its current matching vehicles for review, not a frozen list of VINs or an immediate download. Manual vehicle checkbox choices apply only to the current export. Templates belong to the signed-in local account and current workspace on this PC, survive restart, and are not shared or included in business backup ZIPs. Save, Save as, Update, Rename and Delete affect only these personal preferences.

Exports use one local working-copy snapshot. Export, selection refresh and template management do not publish pending operations or resume paused synchronization. Offline/pending/conflicted data is identified in the dialog; synchronize separately if a current shared view is required. Known deleted identities are excluded, and a missing or no-longer-matching selection must be refreshed rather than silently replaced by another vehicle with the same VIN. Switching, logout or closing the export dialog cancels/discards an unfinished download.

CSV files use UTF-8 BOM, comma delimiters, CRLF rows, quoted special characters and spreadsheet-formula protection. Headers are localized; stored values and dates are not reformatted, and missing values are empty cells. For identifiers such as serial numbers with leading zeros or long numeric codes, use Excel **Data → From Text/CSV** and import those columns as **Text**; double-clicking a CSV can let Excel auto-convert them. Each export is limited to 20,000 selected vehicles and 200 MiB of uncompressed CSV or ZIP data; export smaller batches if needed. This CSV feature did not require a database, shared-protocol or backup-format migration.

## Verified business recovery

Administrators choose Back up data to synchronize team data and download a complete business backup. Synchronization failures or unresolved conflicts stop the download. The local-only backup remains available for maintenance through the API and never starts synchronization. Backups remain unencrypted.

Restore previews validate originals and display searchable effects and field differences. Confirm all archive effects together. Before applying, the service saves and read-back verifies a local safety ZIP under the workspace data directory's `restore-backups/`; failure prevents application. Copies are retained until manually removed and do not replace independent cold backups. Current development backups use format 5 with field version 4; formats 1–4 remain readable. Managed modification publication additionally uses the guarded graph restore and retained-payload recovery described above.

Restore history and results are local administrator records. Durable request IDs prevent reapplication after a lost response; the applied receipt and business changes commit in one transaction. Query results before retrying. Applied results can retry shared publication without applying the ZIP again. Prepared or failed requests require a fresh preview. Published means shared publication completed, not that all clients have refreshed. Permissions, permanent deletions and immutable configuration history are not rolled back. Continue pausing other clients and keeping independent backups for recovery operations.

Recovered business history has its own durable local publication queue, including when current records already match the backup. Pending counts and backup source metadata include this queue. Publication revalidates the restoring administrator and device, preserves original change attribution, and acknowledges the queue only after reading its canonical shared receipt. A failed publication or interrupted acknowledgement can retry after restart without replaying backed-up operations or duplicating history. A second restore must wait for pending history publication. Restored removal of retained legacy fields participates in synchronization and conflict resolution just like a changed value.

Backup reminder: the overview menu contains Back up data, Restore data and Restore history. Online administrators are reminded when the team has no recorded backup or the last completed team-backup transfer was at least seven days ago. Completion time is shared by the team. Remind me tomorrow suppresses the prompt for the administrator on this device for the current local calendar day; work remains available. Local exports and automatic pre-restore safety copies do not reset the timer. Completed HTTP transfer does not verify where the browser saved the file. Old versions do not record completion, so collaborating administrators should use the updated application for reliable reminders.

## Local fault diagnostics

The service writes structured JSON Lines to `<local data directory>/logs/diagnostics.jsonl`. Workspaces opened by that service share this diagnostic destination; no logs are written into the team share by this feature. With default settings the Windows location is `%LOCALAPPDATA%\VehicleManager\data\logs`. An explicit `VEHICLE_MANAGER_DATA_DIR` changes that location. Preserve the existing `startup.log` in the data directory and `launcher.log` beside the launcher when investigating failures before service initialization.

Each diagnostic line includes UTC time, application and Node versions, process ID, severity and event. Failed, aborted and slow (at least two seconds) API requests include status, duration, a safe route template and a server-generated request ID. Successful authentication actions are recorded; ordinary successful polling is omitted. Responses expose `X-Request-Id`; JSON, blob and download API errors retain validated IDs in `ApiError.requestId` without changing the existing error code. In browser developer tools, locate the failed Network request and copy this response header to find the matching log entries. Never include its Cookie, Authorization, workspace token or request body in a support report.

Lifecycle events distinguish starting, ready, stopping, stopped, port/listen failure, state-file failure, shutdown failure and uncaught crashes. Synchronization records phase/error/count changes and slow successful cycles, suppressing identical repeated failures. Status checks and shared-roster polling record failure/recovery transitions even when no HTTP request is active. Parser failures record the error code, byte count and duration without the uploaded filename or report content. Async work admitted from an HTTP request inherits its request ID. Background work has no invented HTTP request ID.

Safe diagnostic metadata excludes passwords, credentials, cookies, session/control/presence/workspace tokens, request bodies, query strings, usernames, VINs, filenames, network paths and business values. Unknown errors retain only their class category, bounded safe error/cause codes and up to eight code-file basenames with line/column numbers; raw messages and full stacks are excluded. Some context is deliberately unavailable: a browser network failure before reaching the server has no server request ID, and a locally served snapshot does not prove current SMB availability.

Retention is the current file plus three archives (`diagnostics.jsonl.1` through `.3`), each at most 2 MiB. Writes are small, synchronous and limited to diagnostic events; logging I/O failures print one generic warning per writer and leave business results unchanged. Disk capacity and filesystem errors can still prevent diagnostic persistence. Files are local troubleshooting evidence, not immutable audit records, business backups or a substitute for cold backups. Restrict access to the data directory. This feature adds no log-download API, external upload, schema, protocol or backup-format change.

To report a failure: record the local time and timezone, the action and displayed error, application version, and the request ID when available. Copy the current diagnostic file and available archives to approved storage; include legacy startup/launcher logs only when needed, reviewing those legacy files for sensitive paths before sharing. Retain original business data untouched. Request IDs identify attempts, not idempotency keys: inspect existing results before retrying an uncertain write. Stop the service before manually removing diagnostic files; do not remove `local.sqlite`, originals, `HEAD.json`, locks or business snapshots to repair a logging problem.

Startup text logs now prefix each new stdout/stderr line and each launcher error/stack line with an ISO 8601 UTC timestamp (`Z`) and its source. The service preloads timestamp handling before the main module, keeps it after a detached launcher exits, and still exits with failure on uncaught exceptions. Existing historical log lines are preserved unchanged; timestamps cannot be reconstructed retrospectively.
