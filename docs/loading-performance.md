# Workspace loading

The business screen now displays an authorized local snapshot before checking the shared folder. Existing rows remain visible during that check. A single `/api/business/workspace` response contains working records, the component-type catalog, current configuration-revision summaries, history and synchronization state; audit and quarantine data are included only for their corresponding views. Published revision details remain on-demand, and protected revision/catalog records are excluded from ordinary working-record lists. Audit access still requires an administrator.

The response fingerprint covers the actual local data, including unpublished edits. When it matches the client's last accepted fingerprint, the server omits the data arrays. The page retains its current arrays and updates synchronization status only as necessary. Requests are bound to the initiating workspace, and superseded responses cannot overwrite a more recent refresh or save.

Background synchronization still acquires the shared lock and verifies the current team/device permissions. It may skip snapshot ingestion only when the same process previously completed ingestion, the validated shared HEAD is unchanged, and there are no pending operations, deletion imports, configuration imports or conflicts. The HEAD reader accepts business protocols 1–4 and rejects protocol downgrades. Errors and maintenance ingestion invalidate this cache. Background checks perform full validation again after five minutes; explicit refresh/sync and maintenance continue to perform full checks. A newly started process always performs full ingestion first. Corruption of an unchanged snapshot or cached attachment may therefore be detected at the next full check rather than each background poll.

The loading optimization requires no additional database schema, shared protocol or backup format changes; the integrated application retains schema 5 and configuration-review protocols 3/4. Existing write version checks, conflict handling, paused-session rules and permanent-deletion protection remain in place. Local-first display can briefly show the last synchronized state until the shared check finishes, and still requires a current access check (with the existing offline fallback).

Validation includes unchanged polling, local/remote edits, conflicts, revoked membership, rollback and malformed HEAD detection, failed attachment retry, periodic and explicit full validation, delayed shared synchronization, paused sessions, remote deletion, stale workspace requests and out-of-order UI responses. Actual latency over the team's Windows network share still needs acceptance testing; local tests do not establish a speedup percentage.

## Shared-folder read refinement (2026-11-10)

Revision history and detail viewing now read the authorized local copy without initiating business synchronization. The revision Refresh button sends `full=1` and retains full shared synchronization. Preview and publication retain their existing locked checks. Per-request roster access, full configuration integrity validation, permanent deletion guards and photo hash/format/final-access checks remain unchanged. Local viewing can show the last synchronized revision until explicit refresh.

Workspace snapshots no longer include the unused `changes` array (up to 1,000 full audit payloads); audit reading remains on the existing paginated history APIs. Record filters are parameterized SQL and still apply canonical deletion filtering. Revision queries reuse a single local record snapshot. Ordinary vehicle version changes no longer remount an unchanged photo; no persistent photo or permission cache was introduced. Original files and no-store HTTP responses are preserved.

Regression evidence checks zero synchronization calls for ordinary revision history/detail, full synchronization on explicit refresh, rejection after canonical membership revocation and omission of unused history from workspace responses. These checks do not establish real SMB latency or a speedup percentage.

## History pagination refinement (2026-11-10)

Local history sort indexes now use ascending `created` values so reverse traversal satisfies both descending timestamp and descending rowid tie order. The three published descending variants are rebuilt once within a local transaction; current indexes are reused on later starts. Unsearched list/count reads avoid the vehicle-table join. Exact totals, 50-entry pages, lazy details, keyword/date filters, exports, access checks and local-first routing remain unchanged. See benchmarks/history-performance.md for the paired synthetic results and measurement limits.

Workspace fingerprints now include a small local `historyRevision` counter. Local INSERT/UPDATE/DELETE triggers advance it in the same transaction as history changes; rollbacks do not advance the committed counter. This restores refresh invalidation for history-only imports and in-place history recovery edits without serializing full audit arrays. The counter and triggers remain local derived metadata, outside shared snapshots and business backup formats. No table columns, local user_version, business protocol or backup format change. First startup on a large preexisting history database can take additional time to rebuild the sort indexes.
