# STELLANTIS Vehicle Data Management

Version 1.2.0, integrated business build. React + TypeScript + Ant Design, Node.js 24 + Express, local SQLite.

## Current Scope

This independent application now includes the agreed vehicle business workflows. Real company Windows/SMB acceptance is still required before production deployment. The existing `vehicle-demo` and `dove-import-preview` are not modified.

Implemented: local registration/login, English default with Chinese selection, persisted language choice, deferred shared-folder setup, read/write/rename checks, explicit team creation, join requests, administrator approval/rejection, existing-identity device binding, role changes, account disablement, device revocation and last-effective-administrator protection. Team management always reads the live shared roster under an exclusive lock; credentials and login sessions remain local. Team rollback detection is also applied before management writes.

Also implemented: vehicle CRUD; structured controller/motor/battery parts; modification and equipment records; installation/removal dates; authenticated attachments; field-level change history; admin-only archiving and restoration; shared business snapshots and conflict handling; DOVE preview/VIN matching/original retention; same-VIN controller and fault comparison; explicitly selected configuration updates with report provenance; JSON export; admin backup and forward restore; local security audit; portable Windows x64 packaging. No vehicles, reports or accounts are seeded.

Not claimed: arbitrary DOVE template compatibility, fault occurrence statistics, automatic diagnosis/release decisions, tamper-proof authorization, automatic disaster recovery, password recovery, scheduled independent backups, instant offline revocation or company endpoint/SMB approval. Original-file storage is private but not encrypted by this application; use approved disk/share protection.

## Build and Run

```powershell
npm ci
npm run build
npm start
```

Open http://127.0.0.1:4410 . The application listens on the local loopback address only. Change `PORT` if this port is occupied. Local data defaults to `%LOCALAPPDATA%\VehicleManager\data`, independently of the extracted application folder; `VEHICLE_MANAGER_DATA_DIR` can select another dedicated local directory. On first start, the launcher safely migrates data from this folder or one adjacent older `vehicle-manager-*` release, verifies the copy, then renames the source to a `data.migrated-backup-*` folder. Stop the old version with its matching `Stop.cmd` first. If multiple old data folders are found, the new version refuses to guess; copy the intended `data/` folder into the new release folder and retry. The old Demo's 4310 port is not used.

Double-click `Start.cmd` to start in the background and open the browser. It reuses the service for this data directory, or chooses a free local port. The service checks open application pages every five minutes and stops gracefully once none remain, with a short reconnect grace period for refresh/navigation. Closing one tab does not stop a service still used by another app tab; hidden, minimized or inactive pages remain connected. A server with no app page opened also stops after the initial five-minute check. Reopen the application with `Start.cmd` after an automatic stop. `Stop.cmd` still verifies the same instance and requests an immediate clean stop; it does not kill unrelated Node.js processes. Pending synchronization settles before the local database closes; offline changes remain queued on disk. The launcher and `npm start` should not be used concurrently for the same data directory. Local `service.json` contains a stop-control secret; do not share it or `data/`.

For development, run `npm run dev:server` and `npm run dev` in separate terminals. Vite uses 4411 and proxies API requests to 4410. Starting another application version against an already-running data directory is refused; stop the existing service with its matching `Stop.cmd` before upgrading.

## First Launch and Shared Path

1. Create a local account; passwords must be 10–128 characters. There are no default credentials. The login and registration screen credits **Developer: TA98755**; this is recognition only, not an account or permission.
2. If the company share is not ready, choose **Set up later**. The path remains unconfigured; no simulated share is silently connected and no remote root is created.
3. Once the share exists, enter a UNC path such as `\\fileserver\team\vehicle-data` and test the connection. The signed-in Windows account must already have SMB/NTFS access. The application does not ask for or store Windows credentials.
4. An existing, empty, dedicated folder may explicitly initialize a team after confirmation. The current account becomes the first administrator. A directory containing another application's files, including the previous Demo's snapshots, is not overwritten or adopted automatically.
5. For an existing team, submit a join request. An approved administrator must verify the person/device and choose a new member identity or bind it to an existing identity. The first local account on another computer is not automatically an administrator.
6. Use the bottom-left account button to open **Personal workspace**. Each login session selects its own team; accounts and passwords remain local. Connect additional teams or switch between connected teams without clearing existing data. A team is identified by its roster ID, not its name or folder path.

The share contains a versioned `team.json` roster and a transient `.vehicle-manager-team-lock/` directory during writes. Approved clients additionally maintain `business/HEAD.json`, immutable `business/snapshots/`, unique `business/operations/` and content-addressed `business/blobs/`. Team and business writes use the same exclusive lock. SQLite merge work is performed on a local temporary copy, not by multiple clients writing a network SQLite WAL. Do not edit shared protocol files manually. A stranded lock requires confirming that every client has stopped and preserving a backup before manual maintenance; locks are never reclaimed merely because they look old. Real SMB behavior still needs multi-computer validation.

Before a breaking team-format upgrade, first install the new release on every device and create a cold backup. An administrator can then enable **Require current version** in Team access; this switches the shared roster to protocol 2 and older releases will be rejected. The action requires two effective administrators so the team retains an approval path. Shared snapshots retain the latest 30 and one per day for 90 days; attachments and original blobs are not currently garbage-collected. Backup restore requires a preview, explicit confirmation of omitted records to archive, and acknowledgement of fields this version does not understand. The preview is invalidated if the backup, local records, deletion markers or pending operations change before restore.

Pending or disabled accounts cannot access the administrator API. Offline status may display the last approved cached identity, but all administrator operations require a successful live shared-folder read. People who can modify the share or local SQLite can bypass normal application controls; this is not tamper-proof enterprise authentication. Copy application code to another computer, not `data/`, session files or another device's identity.

## Personal Workspaces (First Version)

**Personal workspace** contains the team list, connect-another-team, withdraw-request, disconnect-session, resume-sync and sign-out actions. On mobile, use the person icon in the top bar. Business navigation and administrator team management remain separate. Account profile/password editing and permanent workspace deletion are not part of this version.

Team databases, originals, sync cursors, pending operations, conflicts and temporary DOVE previews are isolated. The original team keeps its local database and blob location; subsequent teams use `workspaces/<hashed-team-id>/` under the stable data directory. Moving the data directory to another computer also moves device identity and is not supported. Never copy an existing device identity to another computer. Each account sees only its connected teams; entering business data still requires approved team access.

Switching or disconnecting preserves all local data and does not revoke membership. Explicitly confirm retention if pending changes or conflicts exist. In-flight requests in the same session block switching, and stale pages cannot write after a switch or new login. Reload a stale page before continuing. Distinct sessions can select different teams; ordinary tabs sharing one login cookie also share its selection. The top bar identifies the current team. Selecting or logging back into a workspace with retained pending changes pauses synchronization until you review them and explicitly resume from the personal panel. Other active, sync-enabled sessions for that same workspace may still synchronize its queue. Existing live shared reads are required for administration; offline cached access retains the existing limitations.

Withdrawal updates only the current account/device's pending request under the roster lock; a withdrawn request cannot be approved. If approval wins the lock first, withdrawal fails rather than revoking the approved membership. If the original directory is unavailable, withdrawal fails honestly: you may disconnect locally and connect elsewhere, but ask the original administrator to reject or revoke the remote request. No background cancellation is silently scheduled.

Before first use with existing data, stop the old service and independently copy the complete data directory to a protected backup. Local SQLite schema is version 5. Schema 5 keeps the established tables while preventing older binaries from opening the new immutable revision and component-type data. Migration inspects the actual tables and columns: it supports both incompatible earlier schema-3 layouts (personal-workspace catalog/session structures, or permanent-deletion/quarantine structures), as well as older supported databases, and adds the missing structures without dropping existing data. Workspace selections, identities, sessions, records, queues, conflicts, deletion receipts and quarantined operations are preserved. Before changing an existing database, migration creates and integrity-checks `migration-backups/before-schema5-<uuid>.sqlite` inside that database's local directory, then applies the upgrade transactionally. Nested workspace databases receive the same backup and shape-aware upgrade when first opened; fresh empty databases need no migration backup. Backup failure prevents migration, and interrupted transactions can retry. Database backups contain credentials and sessions and exclude separate blob files, so protect the complete data directory. They are not shareable business exports or independent disaster backups. Older application versions intentionally reject schema 5; rollback requires a stopped service and supervised restoration of a complete pre-upgrade backup, preserving all newer workspaces first. Do not replace a live SQLite file or delete WAL files.

API clients must retain the `X-Workspace-Token` returned on login/status and explicit selection changes and send it for setup configuration, business and team operations. Missing/stale tokens are rejected. Tokens are scoped to a login session and selection epoch; clients must not silently adopt a new token from background status calls over existing forms.

## Business Use

### Configuration revisions

An administrator enables **Configuration revisions** once for the selected workspace, after all collaborating installations upgrade to application 1.2.0. Activation publishes shared business protocol 3; older clients cannot publish to that format. Existing team-roster upgrade rules remain in effect. Each vehicle starts without a published configuration and receives **R01, R02, R03…** only when an approved member publishes a review online with synchronization enabled.

Maintain HV Battery, eMotor, Controllers and Thermal Management in their component sections. Thermal System Type continues to use the existing vehicle value. Administrators can add named component types with common identification fields and notes, rename them or hide them from new selection; historical and queued references retain their identities. All active installed instances are captured, including multiple batteries/motors and legacy extra controller records.

The review pre-fills existing values. Required missing information needs **Unknown** or **Not applicable** with an explanation; absent sections need **Not installed** or **Unknown** with a reason. These explanations belong to the frozen revision and do not rewrite ordinary component fields or DOVE observations. Enter a change summary and optional title, then use one final **Publish revision** action. Cancelling creates no revision; component edits already saved remain saved. Offline component work remains available, but publication requires an online, sync-enabled session; paused sessions must be resumed explicitly in Personal workspace.

Published revisions are read-only and retain VIN, actor, date, component identities and details. Compare revisions or copy their summary from the history tab. The Overview summary and optional **Configuration revision** table/CSV column show the current R number. Relevant component changes show **Unpublished configuration changes**; owner/location/photo changes, save counters and an identical DOVE reimport do not. Corrections create another revision, rather than editing an older one.

Backup format 4 preserves frozen revisions, custom types and durable publication receipts. Formats 1–3 remain accepted. Restoring old working data never archives or replaces published revisions, rolls their maximum R number back, or renames/reactivates current type definitions. Valid missing protected history is staged durably for publication with the working restore under the shared lock; conflicting immutable payloads, duplicate ordinals or broken chains reject restoration. Deleted vehicle UUIDs and their historical child rows remain skipped. Re-registering a VIN uses a new vehicle identity and a separate revision sequence.

Every labeled vehicle **Overview** field can be displayed through **Columns**, including **Compliance Level**. Optional **Nick Name**, **VIN** and **Plate valid until** columns show those values independently of the existing combined Vehicle and License plate columns. **Cooling architecture** can display stored legacy values without restoring that field to the editor. These five choices start hidden and support the same personal ordering, widths and header filters; the original ten default columns remain unchanged. Vehicle Photo and its attachment reference are excluded from the column catalog.

Use the filter button in any vehicle data-column header to search and tick distinct cell values, including **(blank)**, then choose **Apply**. **Reset** clears the checklist; apply it to remove that column's filter. Closing without applying keeps the current filter. Choices cover all vehicles permitted by **Show archived**, across every page. Multiple choices in a column use OR; different columns and the existing search/status/archive controls use AND. Combined cells are one choice, including nickname/VIN, plate/expiry, timestamp/version and joined battery summaries. Filtered headers are highlighted; **Clear column filters** removes all header filters. Hiding a column clears its filter, while resizing and reordering preserve it. Filters remain while navigating within the current account/workspace, but clear on reload, logout or workspace switching. They work offline and while sync is paused, use no saved settings or business writes, and do not change export configuration.

Enable **VCU Type** through **Columns** to display the Type recorded under **Controllers → VCU** as ordinary text. It is hidden by default, starts at 160 pixels wide and uses the existing personal visibility/order/width settings. It shows the same unarchived controller as the VCU slot, including the EVCU alias; a missing controller or blank legacy Type displays `—`. Editing the VCU Type updates the column when the records reload. This is a derived display, with no additional vehicle field or data migration.

The Vehicles table centers its headers and values. Open **Columns** to show/hide and reorder existing fields; Vehicle remains first and Actions last. Model, Color, Thermal System Type, Notes, HV Battery Part Number and HV Battery Serial Number are available in addition to the default columns. Drag a header's right edge to resize; double-click to restore its default width. Keyboard users can focus an edge and use Left/Right (Shift for larger steps), or Home/End for the minimum/maximum width. The layout saves automatically for the authenticated local account in the current workspace, including widths of hidden columns. Check the Saving/Saved status or Retry after a failure. Reset layout restores the default ten columns and widths. These personal settings survive restart but are not synchronized, included in business backups, or linked to CSV export templates.

Open a vehicle using the Action arrow to view its cover photo in Overview. Approved members can upload, replace or remove the cover with a change reason and version check; archived vehicles are read-only. Photos use JPEG/PNG, up to 10 MB, 8,192 pixels per side and 24 megapixels. The original bytes and metadata are retained, without cropping or metadata stripping. Replacing or removing a cover does not delete the old attachment, original blob, history or backup. Photos synchronize through the existing attachment workflow, and offline/paused changes remain queued without resuming synchronization. An unavailable selected photo is never substituted with another attachment. Business backups preserve the cover reference and attachment; older backups restore without a cover. No database, shared-protocol or backup-format migration is required; upgrade collaborating clients together to manage photos consistently.

- Approved users enter **Vehicles** by default. Add a real vehicle, then use its detail drawer for controllers, modifications, equipment, reports, attachments and history. Project code is separate from model. Physical location is optional free text, available when creating or editing a vehicle and shown in the vehicle list and details; it can be searched, changed or cleared later. Upgrade collaborating clients together to expose this field consistently. Serial numbers are text. Controllers contains one fixed VCU, MCU and BMS/MSB per vehicle, without add/install/remove controls. Existing historical records are not deleted.
- **Attachments** accepts `.xlsx`, `.xls`, `.pdf`, `.png`, `.jpg`, `.jpeg` and `.jfif`, up to eight files per queue and 10 MB per file. Select multiple files, review or remove queued rows, then click **Upload** once; files are sent sequentially without another confirmation. Each row shows its result. Invalid files do not block valid uploads, successful files remain saved, and **Retry failed** submits only definite failures. If a response is lost, refresh and inspect the attachment list before clearing the unknown row and selecting that file again; unknown results are never automatically retried. Closing the drawer or changing vehicle/workspace or login stops unsent files; an admitted upload may finish in its original workspace. Extensions are case-insensitive and file signatures must match the supported format. JFIF files use the existing JPEG validation; original filenames and bytes are preserved through download, synchronization and backups. Offline and paused-sync uploads retain the normal attachment behavior without resuming synchronization. Vehicle cover-photo uploads use their separate JPEG/PNG controls.
- Vehicle **Compliance Level** is required when manually creating or editing a vehicle. Choose exactly **Eu7**, **CN6**, **Eu6** or **PL8**; no value is automatically assigned. It appears in **Overview** after Thermal System Type and is included in search, history, synchronization, JSON/CSV exports and backups. Existing vehicles display `—` until classified on their next manual save. Photo changes, archive operations, DOVE workflows and older-backup restoration remain compatible with blank legacy values. No schema, protocol or backup-format migration is needed; upgrade collaborating clients together to preserve the new field when editing.
- **DOVE import** accepts up to eight supported `.xlsx` files in one batch, each up to 10 MB. Matched uploads open an explicit confirmation dialog showing the VIN, current values and all twelve fields for VCU, MCU and BMS/MSB. Only confirmation saves the report and applies valid controller data in one local transaction; cancelling writes nothing. Source conflicts require selection and older reports require acknowledgement. Configuration import is enabled by default and can be disabled for report-only retention. Duplicate originals reuse the report but can reapply configuration after fresh confirmation. Missing and invalid values preserve current data. Preview expires after 30 minutes; at most eight drafts and two parsers are allowed. Parsing runs sequentially within a batch in a child process with a 20-second deadline and 256 MB V8 heap per file, plus ZIP/worksheet limits. These limits are not a promise to accept every workbook under 10 MB.
- If a DOVE report genuinely has **no VIN**, one combined import dialog lets you search existing, unarchived vehicles by nickname, VIN or license plate and review import options. Each file has its own selection; there is no automatic choice, inline vehicle creation, separate selection-confirmation step or ownership checkbox. Selecting a vehicle refreshes only the preview and resets controller import to **report-only**. One final **Confirm import** saves the ready reports; the dialog shows their count and leaves unassigned files pending. Controller updates require explicit opt-in; for manually assigned reports the same final action acknowledges any displayed older-report warning without another checkbox. Cancel before submission saves nothing. Failed rows stay open for correction, while successful rows are not submitted again; cancelling after partial success does not undo saved reports. The workbook bytes and blank original VIN stay unchanged, while a separate immutable association records the vehicle UUID/VIN, actor and assignment time. Malformed or conflicting VINs cannot use this fallback. Changing the selection invalidates old confirmations; archive, deletion or VIN changes require a fresh selection, and a re-registered VIN never silently redirects an old preview. Manual associations survive sync/backups, appear in report viewing and support same-vehicle comparisons/configuration updates. CSV original-report VIN columns stay blank; the linked vehicle VIN is separate. No storage/protocol/backup migration is needed; upgrade collaborating clients together.
- **Reports** supports original download and two-report comparison for the same vehicle UUID and reported or explicitly associated VIN. Duplicate byte-identical originals are deduplicated within the vehicle identity. Differences do not establish repair, correct software or vehicle release. No fault occurrence/trend analysis is performed.
- **Overview** shows vehicle details only. **Controllers** displays name, Type, supplier, product part number, software part number and calibration version for the three fixed controllers; **More** opens the editor. The controller name is fixed. **Type** must be explicitly selected as **Open ECU** or **Close ECU** when manually creating or editing a controller; there is no automatic default. The remaining twelve report fields retain their existing meaning. A change reason is required; cancelling writes nothing, and saving checks the record version and records history. Empty fixed slots can also be filled here without adding duplicate controllers. EVCU maps to VCU; BMS and MSB map to BMS/MSB without altering the original report. **Update vehicle configuration** remains available with source selection and older-report confirmation where required. DOVE/configuration imports preserve Type and may create unclassified controllers; select Type on their next manual edit.
- **HV Battery** includes Part Number, Serial Number, Part Maturity Level and **Life Status**. Every manual battery save requires an explicit choice of **BOL**, **2Y Aged**, **8Y Aged**, **10Y Aged**, **15Y Aged** or **EOL**. Older records remain blank (`—`) until edited; removal-only actions and archive/restore operations remain available without forcing a classification. Controller Type and battery Life Status are separate from legacy `type` and `batteryStatus`, which remain intact. Both fields survive history, sync, JSON/CSV export and backups; CSV exposes **Controller Type** and **Life Status** without changing saved template selections. Older backups remain restorable with blank classifications. No schema/protocol/backup-format upgrade is needed, but upgrade collaborating clients together so old editors do not strip the new fields.
- **Shared sync** shows pending operations, conflicts, quarantined operations and errors. When synchronization is enabled for the session, reads try synchronization first, successful local writes trigger synchronization, and the running service retries every 30 seconds. Offline saves remain queued. A paused session must review retained changes and explicitly resume in **Personal workspace**; permanent-deletion previews, permanent deletion and backup restore remain disabled until then. Backup downloads and read-only quarantine inspection/export stay available with their existing permissions. Other sync-enabled sessions for the same workspace may still synchronize its queue. Shared publication is eventual consistency, not a guarantee that every client updates within 30 seconds.
- Conflicting fields require local/shared choices. Duplicate VIN or an unavailable parent cannot be forced over a canonical shared record. Administrators can review blocked authorization conflicts, and the latest roster governs subsequent submissions. Do not copy a full local database over the shared snapshot.
- **Change history** contains synchronized business changes with actor/device/reason/source. **Device audit log** is administrator-only and displays this computer's login/download/export/backup events; it is not an immutable central security log.

## Administrator Vehicle Deletion and Upgrade

Archive remains reversible. An online administrator with synchronization enabled for the selected workspace can additionally delete an already archived vehicle from its detail drawer. If synchronization is paused, review retained changes in **Personal workspace** and explicitly resume before opening a deletion preview or confirming deletion. The five-minute preview lists the vehicle and all linked record counts; confirm the exact VIN, type `DELETE`, and enter a reason. Cancelling writes nothing. Pending target changes/conflicts must be resolved first, and changed vehicle/child data requires a fresh preview. Deletion removes the vehicle, controllers/parts, modifications, equipment, reports and attachments from current working data, including archived children. It does not purge original blobs, immutable snapshots, audit history or existing backups, and it is not secure erasure.

Deletion is published under the shared lock before success is reported. A dropped response can be retried with the same request; a committed deletion awaiting local refresh is not an ordinary failed deletion. Permanent deletion markers prevent stale offline edits, new offline children and old backups from resurrecting the old record IDs. Blocked local operations and their files remain quarantined: inspect/export them in **Shared sync**; there is no keep-local resurrection option. A VIN can be registered again with a new vehicle identity, and a fresh DOVE preview can retain the same original for that new identity without reviving deleted records.

Before the first deletion, stop other installations, independently back up the shared folder and each local data folder, and deploy this deletion-aware version to **all collaborating clients**. Existing local SQLite databases upgrade to schema 5 on first open, including either earlier schema-3 layout; older binaries cannot open the upgraded local folder. Application version 1.2.0 creates backup format 4 and accepts formats 1–3. Business sync retains protocols 1/2 until configuration revisions are enabled by an administrator, then uses protocol 3; deletion and restoration never downgrade it. Team-roster protocols and upgrade policies remain unchanged. Old separate installations cannot publish to business protocol 2 and may show `SHARE_CORRUPTED`/offline: upgrade them, do not roll back HEAD or delete shared files. Offline cached copies disappear only after an upgraded client reconnects and synchronizes.

The admin APIs are `GET /api/business/vehicles/:id/delete-preview` and `DELETE /api/business/vehicles/:id`; deletion uses an actor-bound preview, current version, exact VIN/confirmation/reason, and an idempotency request ID. Quarantined payloads are read-only at `/api/business/sync/quarantined` and can be exported at `/api/business/sync/quarantined/export`.

## Backup and Restore

Administrators can download an unencrypted ZIP containing records, synchronized history, pending operation payloads, referenced original blobs and a team-roster snapshot. It excludes local passwords and login sessions. Current safety limits are 200 MB total ZIP/expanded content, a 20 MB manifest and 10 MB per blob. Monitor disk capacity; old shared snapshots are retained and not automatically purged. A share snapshot is not a backup in a separate failure domain.

Restore is an online administrator operation: pause other clients and writes, independently preserve the current entire shared directory and local data, finish existing pending operations, select a backup from the same team, type `RESTORE`, and enter a reason. The current administrator session must have synchronization enabled; if paused, review retained changes and explicitly resume from **Personal workspace** before restoring. The application records forward business changes rather than rolling the shared sequence backwards; records outside the backup are archived, not physically deleted. New business changes after the backup may be replaced, so do not restore while others continue editing. Archived vehicles and retained originals are supported. Validate the restored records, history and files and then resume clients.

New backups use format 4 and include permanent deletion markers, retained history, frozen configuration revisions, component types, publication receipts and quarantined operation payloads/files, in addition to current working records and their originals. Formats 1–3 still restore. Canonical deletion markers always win: restore skips deleted vehicle UUIDs and all their linked records and displays skipped vehicle/record counts. It never removes deletion markers or uses backup markers to delete currently live records. Existing archive-extra-record restore behavior remains for working records, while protected configuration history/catalog records are preserved. Deleted-only original blobs remain in existing storage/backups but are not automatically restored to working data.

The roster in the ZIP is preserved for manual identity/disaster investigation; the ordinary business restore UI does not roll back roles, reinstate revoked devices, replace local accounts or silently replay arbitrary historical pending-operation payloads. It restores the backup's record state through newly authorized operations. Lost roster/administrator credentials or incompatible/rolled-back protocol state require a coordinated manual recovery using independently preserved complete data, not pointing `HEAD.json` to an old snapshot and forcing clients onward.

## Configurable CSV exports

Use **Vehicles → Export CSV** to filter the local vehicle list, select vehicles across pages, and choose/reorder columns for vehicles, controllers, modifications, equipment, report summaries and attachment metadata. Different filters combine with AND; multiple values within one filter combine with OR. Archived vehicles and linked records are excluded unless **Include archived** is enabled. Choose English or Chinese headers. The download is always one ZIP with a CSV for each enabled category, including headers-only files when no linked rows exist. Original files, detailed DOVE controller/fault observations, historical snapshots, history and quarantined operations are not included; this export is not a backup.

Named templates remember filters, enabled categories, ordered columns, archive inclusion and header language. Applying a template selects its current matching vehicles for review, not a frozen list of VINs or an immediate download. Manual vehicle checkbox choices apply only to the current export. Templates belong to the signed-in local account and current workspace on this PC, survive restart, and are not shared or included in business backup ZIPs. Save, Save as, Update, Rename and Delete affect only these personal preferences.

Exports use one local working-copy snapshot. Export, selection refresh and template management do not publish pending operations or resume paused synchronization. Offline/pending/conflicted data is identified in the dialog; synchronize separately if a current shared view is required. Known deleted identities are excluded, and a missing or no-longer-matching selection must be refreshed rather than silently replaced by another vehicle with the same VIN. Switching, logout or closing the export dialog cancels/discards an unfinished download.

CSV files use UTF-8 BOM, comma delimiters, CRLF rows, quoted special characters and spreadsheet-formula protection. Headers are localized; stored values and dates are not reformatted, and missing values are empty cells. For identifiers such as serial numbers with leading zeros or long numeric codes, use Excel **Data → From Text/CSV** and import those columns as **Text**; double-clicking a CSV can let Excel auto-convert them. Each export is limited to 20,000 selected vehicles and 200 MiB of uncompressed CSV or ZIP data; export smaller batches if needed. Application 1.2.0 uses local schema 5 and backup format 4; CSV exports retain their existing six categories and template selections.

## Portable Distribution

```powershell
npm run package:portable
```

On Windows x64 this builds a timestamped clean folder and ZIP under `releases/`, including `runtime/node.exe`, its license, runtime dependency licenses, built application, `Start.cmd`, `Stop.cmd` and a short guide. No local database, accounts, test reports or shared path are included. Extract to a writable local folder and double-click `Start.cmd`. Do not run from inside the ZIP or install the application into the team share. Each colleague registers and points to the same existing team.

Package smoke verification uses an isolated directory:

```powershell
node scripts/smoke-portable.mjs "releases\<generated-folder>"
```

It checks the bundled Node runtime, launch reuse, vehicle entry, isolated parser, byte-identical originals, backup and graceful stop. Enterprise application control can still block a portable runtime; obtain IT approval rather than trying to evade policy. Stop and back up before upgrading. Never copy another user's `data/` to initialize a new device.
