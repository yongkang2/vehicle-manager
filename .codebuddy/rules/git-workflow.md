# Git 协作与发布规范（强制）

在本仓库执行任何代码修改时，必须遵守以下流程。违反时先停下来说明原因，而不是直接改代码。

## 一、开发前：同步与隔离

1. **禁止在 `main` / `master` 上直接开发。** 主干必须随时可打包、可发布。
   - 每次开发前：`git checkout main` → `git pull` → `git checkout -b feature/<功能名>`。
2. **明确任务边界。** 按模块或文件拆分任务；若必须改动与他人重叠的文件，先声明星要改的具体位置（如 `business.ts` 白名单逻辑），避免同时改同一段代码。

## 二、开发中：小步提交，及时同步

3. **小步提交，Commit Message 必须可读。** 完成一个小功能或修好一个 bug 就提交一次。
   - 反例：`修改`、`update`
   - 正例：`fix: 修复新版保存时清空旧版冷却架构字段的bug`
   - 采用约定式前缀：`feat:` / `fix:` / `refactor:` / `chore:` / `docs:` / `test:`。
4. **每天开工先同步主干。**
   - `git checkout main` → `git pull` → `git checkout <你的分支>` → `git rebase main`
   - 冲突解决后 `git rebase --continue`。优先 rebase，保持线性历史。

## 三、提交审查：Pull Request

5. **绝不直接 push 到主干。** 一律走 PR/MR，并指定至少一名 Reviewer。
   - 审查重点：逻辑正确性（尤其新旧字段兼容）、边界情况、是否误提交测试环境凭据/密钥。
6. **冲突在本地解决，不在网页上随手点。**
   - 切到自己的分支 → `git pull origin main`（或 merge main）→ 本地核对双方逻辑，保留正确实现 → 测试通过 → 再 push。
7. **合并前必须通过 CI。** `npm run build` 与单元测试必须全绿；跑不过的代码禁止合并。

## 四、合并与发布：安全第一

8. **合并策略使用 Squash and Merge**，把分支上的多次零碎提交压成一条干净的提交记录。
9. **数据库变更是最危险的一步。**
   - 任何包含 `DROP COLUMN`、重命名、类型收窄等破坏性迁移的 PR，必须在全团队确认「旧代码已全部下线」后，**单独发起、单独发版**。
   - 破坏性迁移不得与功能变更混在同一次合并中。
   - 涉及字段增删时，先确认所有读写方（代码、脚本、历史数据）的兼容性，再动 schema。

## 执行约定

- 动手改代码前，先确认当前分支不是 `main`/`master`；若是，先创建特性分支并告知用户新分支名。
- 提交时按上述格式写消息；跨模块的大改动先拆成多次提交。
- 涉及 `server/` 迁移脚本或 `shared/` 类型定义的改动，视为高风险，需额外说明影响面。
